Transport office dashboard

For the office during the school run: one line per bus shows where it is between its stops. Problems surface on their own, in plain language, and the office fixes them without calling a developer.

  • Needs attentionBus late or silent, breakdowns the driver reported, SMS credit running low, a missed backup. Each one says what to do.
  • Cancel or swap a busCancel a trip with a reason that goes to every parent on it, or change the bus or driver before it starts.
  • Set up once a termImport students from a spreadsheet (with row-by-row errors), link parents, place stops by pasting Google Maps coordinates.

What a parent wants at 6:50 am: how many minutes until the bus reaches their stop. Alerts arrive about five minutes before. Parents without the app get the same alerts by SMS, automatically.

Behind the screens

The parts nobody sees, and the reason parents can trust the alerts.

Alert engine

  • Arrival needs proof: two GPS fixes inside the stop's circle, or the bus slowing to a stop, so a bus driving past doesn't count
  • ETAs learn each road's real travel times
  • Late buses warn parents at 10, 20 and 30 minutes, once each
  • Siblings get one message, not three. Quiet hours are respected; urgent alerts always go
  • Push first, SMS if push fails, never both

Built to keep running

  • Nothing lost if the server restarts: alerts are queued in the database
  • Problems are spotted automatically: a silent bus, a stalled bus, a bus that never left
  • Office warnings: SMS credit low, with school days left
  • Nightly backups: checked as readable, copied off-site encrypted, one-command test restore

Ready to deploy

  • One server, one web address, automatic HTTPS
  • Setup: one script prepares a new Ubuntu server, one deploys
  • Automatic deploys: GitHub tests every change and deploys it, but never while buses are out
  • Runbook: registrations, SMS sender ID, Play Store, monitoring, "what to do when"

Where it stands

Built in eight phases, each tested before the next. Here is what has been proven and what only a real server and real phones can prove.

Proven

  • 163 automated tests, including the apps run against the real server code and a real database
  • Every screen clicked through in a browser at phone and desktop size
  • Backups and restores run against a real database; a damaged backup is caught

Needs a real run

  • Building the server images (first GitHub run)
  • Installing the apps on real Android phones
  • Live SMS and push with the school's own accounts

To go live

  • Register with the Data Protection Commissioner
  • Apply for the SMS sender ID and a Google Play account (both take time)
  • Set up the server, pilot Route 1 for a week, then all six buses
